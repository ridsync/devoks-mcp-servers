# Interaction Integrity — 반복·동시 트리거 정합성

하나의 상태에 대해 **확정 시점이 서로 다른 트리거가 겹칠 때**, 마지막에 남는 값이 사용자의 의도와
달라지는 결함군을 다룬다. 코드리뷰·테스트 케이스 설계·실동작 검증이 공통으로 참조하는 SSOT다.

스택 중립 문서 — 특정 프레임워크의 API명 대신 **역할**로 서술한다. 스택별 구체 문법은 프로젝트
active convention(`.claude/rules/project-convention.md`)에서 다룬다.

---

## 1. 적용 대상 판정 (먼저 여기서 걸러낸다)

**두 조건을 모두 만족할 때만** 이 문서의 대응을 검토한다. 하나라도 아니면 적용하지 않는다.

- **(a) 반복 트리거가 실제 사용 패턴인가** — 증감·연속 제출·검색어 타이핑처럼 사용자가 **의도적으로** 반복한다.
  우발적 더블클릭 방지만 필요한 경우는 해당하지 않는다.
- **(b) 그 조작이 상태를 확정하거나 I/O를 유발하는가** — 서버 요청·로컬 저장·값 누적.
  화면 표시만 바뀌는 조작은 해당하지 않는다.

**적용하지 않는 예**

- 라우트 이동, 모달 열기/닫기, 아코디언·탭 토글 등 **표시만 바꾸는** 조작
- I/O 없이 로컬 상태만 1회 바꾸는 단발 조작 → 진행 중 비활성화 한 줄로 충분
- 서버가 이미 멱등성을 보장하는 제출 경로 → C4 대응 불필요

(b)를 만족해도 **필요한 대응만** 고른다 — §2에서 조작의 의미를 분류하면 어느 결함만 해당하는지 정해진다.
**세 결함군을 전부 적용해야 하는 경우는 드물다.** 과적용은 복잡도를 늘려 새로운 결함을 만든다.

> **적용 대상으로 판정됐다면, 개발 머신에서 재현되지 않는 것은 근거가 아니다.** 이 결함군은 저사양 기기·느린
> I/O에서 밀린 이벤트가 한 배치로 처리될 때만 드러난다. 재현 여부와 무관하게 **코드 경로로 판정**한다.

---

## 2. 먼저 조작의 의미를 분류한다 (진입점)

대응 패턴은 결함이 아니라 **조작의 의미**가 결정한다. 여기서 잘못 분류하면 이후 대응이 전부 어긋난다.

| 의미 | 예 | N회 트리거의 정답 | 주로 나는 결함 |
|------|-----|-----------------|--------------|
| **누적 (accumulate)** | 증감 스테퍼, 수량 조절, 카운터 | **정확히 N만큼 반영** | C1 · C3 · C6 |
| **최종값 (last-wins)** | 슬라이더, 검색어, 텍스트 입력, 필터 | **마지막 값만 반영** | C2 · C3 · C5 |
| **단발 (once)** | 제출, 결제, 삭제, 발행 | **정확히 1회 확정** | C4 · C7 |

> **가장 흔한 오적용 — 누적형에 디바운스만 걸기.** I/O 폭주(C3)는 사라지지만 **갱신 유실(C1)은 그대로 남는다.**
> 디바운스는 최종값형의 도구다. 누적형은 "값 계산"과 "I/O 코얼레싱"을 분리해야 한다.

## 3. 결함 클래스

| ID | 결함 | 발생 조건 | 증상 |
|----|------|----------|------|
| **C1** | Lost update | 다음 값 = f(이전 값)인데 이전 값을 **렌더 스냅샷**에서 읽음 + 트리거가 한 배치로 처리 | N번 눌러도 1번만 반영 |
| **C2** | Late-response overwrite | 비동기 완료 후 **응답값으로 화면 상태를 되쓰기** | 늦게 도착한 과거값이 더 새로운 입력을 덮음 |
| **C3** | Uncoalesced I/O | 트리거마다 독립 I/O 발생 | 큐 적체 → 반응 지연, 쿼터·요금 낭비 |
| **C4** | Duplicate effect | 단발이어야 할 조작이 재진입 가능 | 제출 연타 → 주문 2건, 중복 리소스 생성 |
| **C5** | Out-of-order response | 여러 요청의 응답 순서가 뒤바뀜 | 이전 검색어의 결과가 최신 결과 위에 표시 |
| **C6** | Pending work dropped | 코얼레싱 대기 중 화면 해제·경로 이탈·백그라운드 전환 | 마지막 값이 저장되지 않음 |
| **C7** | Failure without rollback | 낙관적 반영 후 I/O 실패를 무시 | 화면엔 반영, 실제로는 미저장 (암묵적 실패) |

## 4. 대응 패턴과 함정

패턴만 고르면 오적용한다 — **함정을 함께 확인한다.**

| 패턴 | 해결 | 함정 |
|------|------|------|
| Debounce (마지막 값 1회) | C3 | 대기 중 이탈하면 **마지막 값 유실**(C6). 지연을 늘릴수록 유실 창이 커진다 |
| Throttle (첫 트리거 즉시) | C3 | **마지막 값이 버려진다** → 최종값형에 부적합 |
| 최신 원천 분리 — 이벤트 경로는 갱신 즉시 반영되는 원천(가변 참조 또는 함수형 갱신)에서 읽고, 렌더 상태는 그 파생 | C1 | 원천은 렌더를 트리거하지 않는다. **단방향(원천 → 렌더 상태)일 때만 허용** — 양방향 동기화하면 파생값 중복 보관과 같은 drift가 된다 |
| 낙관적 업데이트 (입력 즉시 화면 반영) | C2 | **롤백 앵커(마지막 확정값)를 보관하지 않으면** 실패 시 복구 불가 → C7로 전이 |
| 요청 취소 (취소 토큰류) | C2 · C5 | **취소 불가 I/O**(로컬 저장, 이미 커밋된 요청)에는 쓸 수 없다 |
| 응답 순번 대조 (요청마다 순번 부여, 최신 것만 반영) | C5 | 취소 불가 I/O의 유일한 대안. 순번 보관 위치가 화면 생명주기 밖이면 리셋 누락 |
| 재진입 가드 (진행 중 플래그·버튼 비활성) | C4 | **클라이언트 단독으로는 불완전** — 네트워크 재시도·중복 탭에서 뚫린다 |
| 멱등성 키 (idempotency key) | C4 | **서버 계약이 필요하다.** 클라이언트만 고쳐서 끝낼 수 없다 |
| 큐 직렬화 | C1 · C5 | 순서는 보장되나 **지연이 누적** — 누적형 UI의 반응성과 상충 |
| 경계 flush (화면 해제·경로 이탈·백그라운드 전환·앱 종료 시 대기분 강제 확정) | C6 | 어느 경계까지 잡을지 명시적으로 결정한다. 모바일은 백그라운드 전환이 추가 경계 |
| 실패 시 롤백 + 사용자 고지 | C7 | silent catch·implicit fallback 금지 — 조용히 되돌리면 사용자는 저장된 줄 안다 |

## 5. 검증 축

값 대조만으로는 절반만 잡힌다. 네 축을 **각각** 확인한다.

| 축 | 방법 | 잡는 결함 |
|----|------|----------|
| ① 트리거 방식 구분 | **간격 없는 연속 호출**(한 배치)과 **간격을 둔 반복**(30~50ms)을 각각 실행 | C1 |
| ② 기대값 수치화 | "입력 N회 × 단위"로 기대치를 수치로 적고 대조 (문구 확인만으로는 부족) | C1 · C2 |
| ③ **I/O 횟수 관측** | 요청 수·저장 호출 수를 **센다**. 최종값만 맞아도 코얼레싱이 없으면 실패 | C3 · C4 |
| ④ 대기 중 이탈 | 연타 직후 즉시 화면 이탈·백그라운드 전환 후 저장값 확인 | C6 |

> **③이 없으면 C3는 원리상 검출되지 않는다** — 코얼레싱이 전혀 없어도 최종값은 정확할 수 있기 때문이다.
> **①만 간격 반복으로 실행하면 C1은 통과로 오판된다** — 한 배치로 몰릴 때만 드러나는 결함이다.

## 6. 이 문서를 인용하는 쪽의 규칙 (드리프트 방지)

소비 문서(리뷰 체크리스트·테스트 품질 기준·검증 절차·스택 convention·FRD 저작 규칙)는 아래만 쓴다.

- 자기 역할의 **판정 질문**(리뷰=발견형 / 테스트=케이스형 / 검증=실행형 / 스펙=요구형)
- **결함 ID(C1~C7)** 참조

**메커니즘 설명("왜 유실되는가")·대응 패턴·함정은 소비 문서에 복사하지 않는다** — 이 문서가 SSOT다.
결함 정의나 패턴이 바뀌면 **이 문서만 고친다.** 소비 문서는 §2 의미 분류가 바뀔 때만 손댄다.

스택 고유 문법(구체 API·코드 형태)은 반대로 **이 문서에 올리지 않는다** — 프로젝트 active convention 소관이다.
